# PRD — Opidence · 2차 프로젝트

Nov 17, 2026 · @새이PD

## 1. 한 줄 요약과 배경

인터뷰 기록에서 인사이트를 정리하고, 모든 인사이트에 원문 근거를 붙여 주는 웹 서비스를 5일 안에 만든다.

- **서비스 이름**: Opidence(오피던스) — Opinion + Evidence를 합친 이름. 모든 의견에 근거를 붙여 정리한다.
- **형태**: 배포 주소에서 동작하는 웹 서비스 1개, 개인 프로젝트
- **직군 관점**: 프로덕트 디자이너. "근거를 어떻게 보여 주어야 사람이 결과를 믿고 쓸 수 있는가"를 화면 설계 판단으로 푼다.
- **프로젝트 목표**: 문제 정의 → 제작 → 수치 확인 → 설명을 하나의 이야기로 만든다. 개인은 핵심 흐름 1개와 지표 1개 이상, 메뉴 2개 이상이 필요하다. (출처: Notion 「2차 프로젝트 가이드 (작성 예정)」 01·02)

## 2. 문제 정의

UX 디자이너나 리서처가 인터뷰 5\~8건을 마친 뒤 팀에 공유할 인사이트를 정리할 때, 인사이트마다 원문 근거를 찾아 붙이는 일이 느리고 틀리기 쉽다는 것이 문제다. 아래 내용은 모두 **검증 전 가정**이며, 확인 시점을 함께 정해 둔다.

| 가정 | 확인 방법 | 확인 시점 |
| --- | --- | --- |
| 근거 발언을 다시 찾는 데 정리 시간의 상당 부분이 든다 | 같은 샘플 전사본을 도구 없이 직접 정리하고 시간을 기록한다 (기준선) | 1일차 |
| AI에게 요약을 맡기면 원문에 없는 말이 섞일 수 있다 | AI가 붙인 인용을 원문과 대조해 일치율을 잰다 | 4일차 |
| 인사이트 옆에 원문이 바로 보이면 읽는 사람이 결과를 더 쉽게 믿고 쓴다 | 사용성 테스트에서 근거 찾기 과업의 성공률과 시간을 본다 | 3\~4일차 |

디자이너 관점의 질문은 "AI가 정리해 주는가"가 아니라 \*\*"정리 결과를 읽는 사람이 어디까지 믿어도 되는지 화면이 알려 주는가"\*\*다.

## 3. 타깃 사용자와 사용 장면

주 사용자는 인터뷰를 직접 진행한 UX 디자이너·리서처이고, 보조 사용자는 그 결과를 받아 보는 팀원이다. 아래 표는 가정이며, 1일차에 주변 2\~3명에게 보여 주고 고친다.

| 사용자 | 사용 장면 | 하고 싶은 일 | 걱정되는 점 |
| --- | --- | --- | --- |
| 인터뷰를 진행한 디자이너·리서처 (주) | 인터뷰 직후 정리할 때 | 비슷한 발언을 묶고 인사이트마다 근거를 붙인다 | 근거를 찾다가 시간이 가고, 인용이 틀릴까 걱정된다 |
| 결과를 받아 보는 PO·개발자·디자이너 (보조) | 공유 자료를 읽거나 회의 중일 때 | "이 말은 누가 한 거예요?"를 바로 확인한다 | 요약만 보고는 믿을 수 있는지 판단하기 어렵다 |

## 4. 목표와 성공 지표

핵심 지표는 사용성 테스트의 **근거 찾기 과업 성공률과 소요 시간**이고, 근거 일치율은 "빨라졌지만 틀리지 않았는가"를 확인하는 보조 지표다. 지표 1개 이상으로 개선 전후를 비교해야 한다는 가이드 기준(제작 원칙 2번)을 따른다.

| 구분 | 지표 | 정의와 측정 | 목표값 |
| --- | --- | --- | --- |
| 핵심 | 과업 성공률 | 참가자 3\~5명이 "이 인사이트의 근거 발언을 찾으세요"를 맞게 수행한 비율 | 1일차 기준선(도구 없이 수행) 측정 뒤 확정 |
| 핵심 | 소요 시간 | 같은 과업의 완료 시간. 도구 없이 할 때와 도구를 쓸 때 비교 | 1일차 기준선 측정 뒤 확정 |
| 보조 (품질 가드레일) | 근거 일치율 | AI가 붙인 인용 20\~30건 중 원문과 정확히 맞는 비율 | 임시 90% 이상, 1일차에 멘토와 조정 |

목표값을 지금 정하지 않는 이유는 기준선 없이 정한 숫자가 근거 없는 숫자이기 때문이다. 90%도 임의의 임시값이다.

## 5. 핵심 흐름

핵심 흐름은 전사본 업로드에서 검색 · 찾기까지 1개이고, **근거가 원문과 맞지 않으면 지어내지 않고 "근거 없음"으로 표시하는 것**이 가장 중요한 설계 판단이다.

```text
[전사본 업로드] → [형식·개인정보 검사]
   ├─ 문제 있음 → [경고하고 업로드 중단] → (다시 올리기) → [전사본 업로드]
   └─ 통과 → [주제 분류 생성] → [근거 연결 + 원문 대조]
                                  ├─ 원문과 일치 → [근거 보기 화면] → [검색 · 찾기 (인용 첨부)]
                                  └─ 불일치 → [근거 없음 상태로 표시]
```

경고 상태와 "근거 없음" 상태는 오류 화면이 아니라 정상 화면으로 설계한다. 원문 대조는 AI가 발언 ID만 돌려주게 하고, 그 ID가 실제 참가자 발언인지 확인하는 방식으로 구현한다.

**설계 판단과 맞바꾼 것**

- **검사를 맨 앞에 둔다**: 개인정보가 AI 호출과 DB 저장 단계로 넘어가기 전에 막으려는 것이다.
- **대조 단계를 둔다**: AI가 만든 인용이 원문에 있는지 사람이 매번 확인하지 않게 하려는 것이다. 효과는 근거 일치율로 확인한다.
- **맞바꾸는 것**: 대조 단계 때문에 응답이 느려질 수 있다. 측정 전 가정이며 4일차 소요 시간 측정에서 확인한다.

## 6. 범위: 하는 것과 뺀 것

5일 안에 끝내려고 **핵심 흐름 1개(전사본 → 주제 분류 → 근거 연결 → 검색 · 찾기)만** 만든다. 뺀 기능과 이유를 발표에서 설명한다. (가이드 02 "5일 범위 팁")

| 구분 | 항목 | 이유 |
| --- | --- | --- |
| 한다 | 텍스트 전사본 업로드 (최대 10건: 샘플 8건 + 시연용 2건). 여러 파일을 한 번에 올릴 수 있고, 발언 번호가 없어도 규칙으로 자동 정리한다(AI 없이) | 핵심 흐름의 시작점이다 |
| 한다 | 주제 분류와 근거 인용 연결 | 서비스의 핵심 가치다 |
| 한다 | 근거 검색 · 찾기, 근거 없음 표시 | 믿을 수 있는지 판단하는 장치다 |
| 한다 | 이름·연락처 등 개인정보 경고 | 안정성 항목에서 막을 것 중 하나다 |
| 뺀다 | 음성 파일 → 글 변환 | 5일 범위를 넘는다. 필요하면 프로젝트 시작 전에 따로 처리한다 |
| 뺀다 | 영어 등 다국어 인터뷰 | 데이터를 한국어로 정해 범위를 줄인다 |
| 뺀다 | 드래그로 옮기는 어피니티 보드 | 화면 구현 비용이 크고 핵심 가치와 직접 관련이 적다 |
| 뺀다 | 설문, FGI 등 다른 리서치 데이터 | 핵심 흐름 1개에 집중한다 |
| 뺀다 | 팀 협업, 여러 사용자 관리 | 개인 프로젝트 범위를 넘는다 |

## 7. 디자인 원칙과 화면 설계

화면 설계의 중심은 \*\*"근거가 먼저 보이고, 모르면 모른다고 말하는 것"\*\*이다. 원칙 3개와 화면 4개, 그리고 비교할 디자인 대안 2개를 정한다.

**디자인 원칙**

1. **근거가 먼저다**: 모든 인사이트 옆에 원문 인용이 있고, 클릭 한 번 안에 원문 위치에 닿는다.
2. **모르면 모른다고 말한다**: "근거를 찾지 못했다"를 오류가 아니라 정상 결과로 설계한다. 검색 · 찾기에서 근거 없는 문장은 기본으로 숨기고, "근거 없는 문장 n개 보기"로 펼치면 "근거 없음" 라벨과 함께 보여 준다.
3. **눈으로 대조할 수 있다**: 인용 문장 강조, 참가자 라벨(참가자 A), 몇 번째 발언인지를 함께 보여 준다.

**화면과 상태**

| 화면 | 목적 | 꼭 설계할 상태 |
| --- | --- | --- |
| 업로드·목록 | 전사본을 올리고 상태를 본다 | 빈 상태(아직 없음), 업로드 중, 형식 오류, 개인정보 경고 |
| 주제 분류 | 인사이트 묶음과 근거 개수를 본다 | 분석 중(로딩), 결과 없음, 분석 실패 |
| 근거 보기 | 인용 원문과 앞뒤 맥락을 본다 | 긴 텍스트, 작은 화면 |
| 검색 · 찾기 | 근거를 물어보고 답을 인용과 함께 본다 | 근거 없음, 응답 지연, 응답 실패 |

**디자인 대안 비교** (가이드 "꼭 보여 줄 것": 대안 비교, 화면 결정의 근거)

- **A안**: 답변 아래에 인용 목록을 모아 둔다. 구현이 쉽다.
- **B안**: 답변 문장 옆에 번호를 붙이고, 옆 패널에서 번호별 원문을 본다. 대조가 쉬울 것이라는 **가설**이다.
- 3\~4일차 사용성 테스트에서 두 안으로 같은 과업을 수행하게 하고 성공 여부, 시간, 막힌 지점을 비교한다. 참가자가 3\~5명이라 통계적 결론은 아니고 정성 비교로 해석한다.

## 8. 안정성과 개인정보

이상 입력, 실패, 빈 화면, 민감정보 중 **2가지 이상을 막고 시연 영상에서 보여 주는 것**이 목표다. 아래 6가지를 모두 구현하되, 영상에는 방어 장면을 최소 2개 넣는다. (출처: 가이드 04 평가 기준 "안정성", 05 제출물 "시연 영상")

| 위험 | 막는 방법 | 시연 장면 |
| --- | --- | --- |
| 빈 파일·빈 입력 | 업로드를 막고 안내 문구를 보여 준다 | 빈 파일을 올린다 |
| 너무 긴 전사본 | 글자 수 제한을 안내하고 나누어 올리게 한다 | 제한을 넘는 파일을 올린다 |
| 근거 없는 질문 | "원문에서 근거를 찾지 못했다"고 답한다 | 전사본에 없는 내용을 묻는다 |
| AI 호출 실패·키 누락 | 화면 안에 사용자 말로 안내하고, 입력한 질문과 결과는 지우지 않는다. 연결 끊김·시간 초과처럼 다시 하면 될 수 있는 실패에만 "다시 시도" 버튼을 둔다. 키·모델 이름·크레딧 같은 원인은 개발 환경에서만 보여 주고 배포 환경에서는 서버 기록에만 남긴다. 키는 `.env`·Secrets에만 둔다 | 키를 일부러 빼고 실행한다 |
| 개인정보 포함 | 이름·연락처 형태를 감지해 올리기 전에 경고한다 | 가짜 연락처가 든 파일을 올린다 |
| 다른 사용자 데이터 접근 | DB를 쓰므로 RLS를 설정한다 | 접근이 막히는 결과를 확인한다 |

영상과 레포에는 키, 토큰, 개인정보가 보이지 않게 한다.

## 9. 고른 메뉴와 AI 사용 지도

**Supabase DB와 RAG 챗봇, 2개를 고른다.** 개인은 2개 이상이면 된다. (출처: 가이드 02 "인원별 골라야 하는 수") README에 아래 두 표를 그대로 옮겨 적는다.

**고른 메뉴**

| 메뉴 | 어디에 썼나 | 맡은 사람 |
| --- | --- | --- |
| Supabase DB | 전사본, 인사이트, 근거 인용 저장. `db.md` 설계와 RLS 적용 | 나 |
| RAG 챗봇 (LangChain) | 전사본에서 근거 문장을 찾아 답하고 인용을 붙이기 | 나 |
| (선택) Playwright QA | 핵심 흐름 자동 테스트. 시간이 남으면 추가 | 나 |

**AI 사용 지도** (초안, 작업하며 채운다)

| 부분 | 만든 도구 | 쓴 프롬프트·스킬 | 사람이 결정한 것 |
| --- | --- | --- | --- |
| 주제 분류 | OpenAI API | `prompts/묶음.md` v1 → v2 | 묶음 기준과 이름 |
| 근거 연결·검색 · 찾기 | RAG | `prompts/근거.md` v1 → v2 | 인용 허용 규칙, 근거 없음 판단 |
| 화면 | Claude Code, Claude Design | CLAUDE.md의 화면 규칙 | 근거 표시 방식(A안·B안) |

**데이터 구조 초안**: 전사본(참가자 라벨, 본문), 발언(발언 ID, 화자, 문장), 인사이트(제목, 요약), 근거(인사이트, 전사본, 인용 문장, 위치). 최종 구조는 `db.md`에 쓴다.

## 10. 데이터 계획

공개 배포에는 **직접 만든 가상 인터뷰 8건(참가자 A\~H)**만 쓴다. 가이드가 개인정보와 내부 자료를 넣지 않는다고 하기 때문이다. (출처: 가이드 01 제작 원칙 1번)

- **언어**: 한국어만 쓴다. 주제는 공공자전거 앱 이용 경험이다.
- **참가자 표기**: 실명, 연락처, 직장, 학교 없이 "참가자 A\~H"로만 쓴다. 모든 줄에 발언 ID(예: A-04)를 붙여 근거를 ID로 가리킨다.
- **까다로운 경우를 일부러 넣는다**: 서로 모순되는 발언, 같은 뜻의 다른 표현, 근거가 약한 주장, 구어체와 오탈자, 길이 차이가 큰 전사본, 남에게 들은 말과 확인되지 않은 추측, 진행자 발화.
- **정답 라벨**: 근거 일치율을 재려고 "이 인사이트의 정답 인용" 20\~30개를 직접 표시해 둔다.
- **한계 명시**: 가상 데이터는 실제 참가자의 발화와 다르다. 발표 회고에 이 한계를 직접 쓴다.

실제 인터뷰를 글로 옮겨 익명화한 뒤 검증에만 쓰는 방안은 동의 범위와 가이드 해석을 확인해야 해서 13번 열린 질문에 올렸다.

## 11. 검증 계획

3일차 상호 테스트와 4일차 측정을 합쳐 **사용성 테스트 3\~5명, 근거 일치율 20\~30건**으로 검증한다. 가이드는 테스트 참가자 3\~5명이면 충분하다고 한다. (출처: 가이드 01 제작 원칙 2번)

| 검증 | 방법 | 기록할 것 |
| --- | --- | --- |
| 개선 전후 비교 | 같은 과업을 도구 없이 할 때(기준선)와 도구를 쓸 때 수행 | 성공 여부, 소요 시간 |
| 근거 찾기 과업 | "이 인사이트의 근거 발언을 찾으세요" 등 과업 3개 | 성공 여부, 시간, 막힌 지점 |
| 디자인 A/B | 같은 참가자가 A안과 B안으로 같은 과업 수행 (순서는 섞는다) | 시간, 헷갈린 지점, 선호와 이유 |
| 근거 일치율 | AI 인용 20\~30건을 원문과 대조 | 일치 개수, 틀린 인용의 유형 |
| 실패 원인 분석 | 틀린 인용을 원문에 없음, 문맥 바뀜, 화자 틀림 등으로 분류 | 유형별 개수, 프롬프트 수정 내용 |

표본이 작아 일반화할 수 없으므로 결과는 "이 조건에서 관찰된 경향"으로 쓴다. 발표 4번 "평가 리포트"에는 지표, 전후 비교, 실패 원인 분석을 함께 담는다.

## 13. 리스크와 열린 질문

가장 큰 리스크는 **AI가 원문에 없는 인용을 만들어 내는 것**이고, AI가 인용 문장을 직접 쓰지 않고 발언 ID만 돌려주게 하고, 화면의 인용은 저장된 원문에서 꺼내 보여 주는 방식으로 대응한다. 그러면 화면의 인용은 항상 실제 원문이고, 남는 위험은 엉뚱한 ID를 고르는 것뿐이며 이것을 근거 일치율로 잰다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| AI가 없는 인용을 만든다 | 서비스 신뢰가 무너진다 | AI는 발언 ID만 돌려주고, 없는 ID나 진행자 발언 ID는 "근거 없음"으로 표시한다 |
| 5일 범위를 넘긴다 | 배포나 측정이 빠진다 | 핵심 흐름 1개만 만들고 뺀 기능 목록을 지킨다 (6번) |
| 가상 데이터만 쓴다 | 실제 상황과 다를 수 있다 | 발표 회고에 한계로 쓴다 |
| 개인정보가 섞인다 | 제출 불가 사유가 된다 | 업로드 전 경고, 제출 전 레포·영상 점검 |
| 테스트 참가자가 적다 | 결과를 일반화할 수 없다 | "관찰된 경향"으로만 쓴다 |
