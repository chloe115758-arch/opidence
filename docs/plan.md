각 단계가 끝나면 실행 방법과 브라우저 확인 방법을 알려 주고, 승인 뒤 다음 단계로 간다.

### 1단계 — 화면 뼈대 (가짜 데이터)

- 파일: `app/layout.tsx`, `app/page.tsx`(업로드·목록), `app/insights/page.tsx`(주제 분류), `app/transcripts/[label]/page.tsx`(근거 보기), `app/ask/page.tsx`(검색 · 찾기 A안·B안), `app/loading.tsx`, `components/Nav.tsx`, `components/Quote.tsx`, `lib/types.ts`, `lib/evidence.ts`(+테스트), `lib/mock.ts`
- 가짜 데이터는 실제 인터뷰와 **다른 주제**(도서관 좌석 예약 앱, 참가자 X·Y)로 만든다. 실제 8건의 묶음 예시를 미리 보면 1일차 기준선 측정이 흐려지기 때문이다.
- 확인: `npm run dev` → `localhost:3000`. 네 화면 이동, 인용 카드 클릭 한 번으로 원문 발언 강조, "근거 없음" 카드, `/ask`의 A안·B안과 "근거 없는 문장 n개 보기", `/?empty`의 빈 상태와 샘플 버튼.
- 1단계가 끝나면 뼈대를 Vercel에 먼저 올려 둔다(PRD 2일차 체크포인트 대비, 선택).

### 2단계 — Supabase 연결

- 파일: `supabase/migrations/0001_init.sql`, `lib/supabase/server.ts`, `proxy.ts`(세션 갱신), `lib/transcript.ts`(+테스트: 파싱·형식 검사·개인정보 검사), `lib/store.ts`(저장·조회), `app/actions.ts`(업로드, 삭제, 샘플 불러오기), `components/Upload.tsx`(업로드 입력, 실행 버튼), `app/error.tsx`(다시 시도 화면), `docs/db.md`, `.env.example`
- 샘플 불러오기는 `data/interviews/`의 8건을 일반 업로드와 같은 검사·저장 경로로 넣는다.

### 3단계 — 주제 분류 + 원문 대조 (2026-11-19 범위 변경)

근거 테이블은 `status` 없이 저장할 수 없어서, 원래 4단계였던 원문 대조와 저장을 3단계에서 함께 한다.

- 파일: `supabase/migrations/0002_analysis.sql`, `supabase/migrations/0003_analysis_limit.sql`, `prompts/묶음.md`, `lib/cluster.ts`(+테스트: 응답 형식 검사, 보낼 글, 프롬프트 버전), `lib/ai/cluster.ts`(서버 전용, OpenAI 호출), `app/insights/actions.ts`, `app/insights/page.tsx`, `components/Analyze.tsx`, `lib/store.ts`, `docs/db.md`
- AI에는 진행자·참가자 발언을 화자와 발언 ID를 붙여 보내고 `{title, summary, utterance_ids}`만 정해진 JSON 형식(최대 8개)으로 받는다. 형식이 틀리면 저장하지 않는다.
- 받은 ID는 `lib/evidence.ts`로 대조한다: 참가자 발언과 정확히 일치하면 `verified`, 없으면 `not_found`, 진행자면 `moderator`. 고쳐 주지 않고 다시 묻지 않는다.
- 다시 분석하면 기존 인사이트·근거를 지우고 새로 만든다(DB 함수 `replace_insights`, 한 트랜잭션).
- 사용자당 하루 10회(한국 시간 자정 기준). OpenAI 응답이 온 분석은 저장에 실패해도 1회로 세고, 요청이 거부돼 응답이 없던 실패(모델 이름 오류, 형식 거부, 크레딧 부족)는 세지 않는다(`0003_analysis_limit.sql`). 화면에 "오늘 남은 분석 n회"를 보여 준다.
- 분석 기록(`analysis_runs`)에 탈락한 ID와 이유, 근거 일치율 재료, 토큰 수, 걸린 시간을 남긴다. 4일차 실패 원인 분석에 쓴다.
- 프롬프트는 `prompts/묶음.md`에 v1부터 쌓는다. 코드는 가장 아래 버전을 쓴다.
- 확인: "분석하기" → 묶음 카드와 인용(DB 원문), 다시 분석하면 교체, 11번째는 막힘, 키가 없으면 안내.

### 4단계 — 탈락 사례 강제 확인

- 파일: `lib/ai/fixture.ts`(`MOCK_AI=1`이면 아래 6개 묶음의 가짜 응답), `lib/ai/cluster.ts`(`MOCK_AI=1`이면 OpenAI 대신 fixture, `NODE_ENV=production`이면 무시, 기록의 `model`은 `mock`), `lib/fixture.test.mjs`, `.env.example`
- 가짜 묶음: ① 정상 3개 ② 정상 1 + 없는 ID + 진행자 ID ③ 전부 탈락 ④ 소문자·앞 공백으로 바꾼 ID(고쳐 주지 않는다) ⑤ ID 없음 ⑥ 같은 ID 2번(합쳐진다). ID는 사용자의 전사본에서 골라 쓴다.
- 확인(코드): `npm test`가 묶음별 `verified`·`not_found`·`moderator` 기대값을 검사한다.
- 확인(화면): `.env.local`에 `MOCK_AI=1`을 넣고 서버를 다시 시작한 뒤 "다시 분석하기" → ②③④가 "근거 없음"(중립 색, 사유 문구)으로 보이고 ⑤는 "이 묶음에는 연결된 발언이 없습니다" 안내가 나온다. `analysis_runs.dropped`에 `not_found`·`moderator`가 묶음 제목과 함께 남는다(조회문은 `docs/db.md`).
- 주의: 가짜 분석도 하루 10회에 센다. 끝나면 `MOCK_AI`를 지우고 서버를 다시 시작한 뒤, 진짜 분석을 1회 돌려 묶음을 되돌린다.

### 4일차 측정 — 같은 전사본으로 3회 분석해 묶음이 얼마나 흔들리는지 보기

배경: 같은 전사본인데 11-19에는 묶음 7개, 11-20에는 6개가 나왔다(`analysis_runs`). 모델 출력이 매번 조금 다르다는 것을 숫자로 확인한다.

- 고정할 것: 같은 전사본(샘플 그대로, 중간에 올리거나 지우지 않는다), 같은 `prompts/묶음.md` 버전, 같은 `OPENAI_MODEL`. 하나라도 바뀌면 비교하지 않는다.
- 방법:
  1. `/insights`에서 "다시 분석하기"를 3회 한다. 분석 1회가 하루 10회 제한에서 1회씩 빠진다.
  2. **매 분석이 끝나면 화면의 묶음 제목과 묶음별 근거 ID를 바로 적어 둔다.** 다시 분석하면 이전 인사이트와 근거가 지워지므로(`replace_insights`) DB에는 마지막 1회분만 남는다.
  3. 3회 모두 끝난 뒤 SQL Editor에서 `analysis_runs`의 `cluster_count`, `id_verified`, `id_total`, `duration_ms`, `status`를 본다(`docs/db.md`의 조회 예).
- 비교할 것: ① 묶음 수(3회의 최소~최대) ② 같은 주제로 보이는 묶음이 3회 모두에 나오는가(제목은 달라도 근거 ID가 많이 겹치면 같은 묶음으로 본다) ③ 근거 일치율(`id_verified / id_total`)이 3회 모두 100%인가 ④ 어느 회차에만 나온 묶음이 있는가.

   - **서비스 설정 문제(키 누락·모델 이름 오류·크레딧 부족·요청 거부)의 배포 문구**는 "지금은 찾을 수 없어요. 서비스 쪽 문제라 직접 고칠 수는 없어요. 나중에 다시 시도해 주세요. 이번 시도는 횟수에서 빠졌어요."로 한다(분석은 "찾을"을 "분석할"로). "다시 시도" 버튼은 두지 않는다. 원인(키, 모델 이름, 크레딧)은 개발 환경에서만 화면에 보이고 배포에서는 서버 기록(`console.error`)에만 남긴다(6단계 결정 1).
   - **지우기 확인 창에 함께 사라지는 것을 알린다.** DB의 외래 키(`on delete cascade`)를 실제 DB에서 확인했다: 전사본을 지우면 그 전사본의 발언(`utterances`), 그 발언을 가리키는 근거(`evidence`), 발언 임베딩(`utterance_embeddings`)이 함께 지워진다. 묶음(`insights`)과 분석·검색 기록(`analysis_runs`, `search_runs`)은 지워지지 않는다(묶음은 남고 근거만 줄며, 근거가 모두 없어지면 "근거 없음"으로 보인다). 문구는 이 사실만 쓰고, 브라우저 기본 창에서 읽기 쉽게 짧게 쓴다: "참가자 A 전사본을 지울까요? 발언 16개와, 이 발언을 쓴 근거가 함께 사라져요. 묶음은 남아요. 지우면 되돌릴 수 없어요." 창 자체를 Montage 다이얼로그로 바꾸는 것(위험 동작에 맞는 "지우기/취소" 버튼)은 나중에 한다.
   - **범위**: 6-4는 아래 표(오류·제한·진행·확인 창)까지만 하고, 바로 이어서 **6-4b**로 나머지 화면의 설명과 빈 상태 문구를 해요체로 통일한다. 11/27 사용성 테스트 전에 한 화면 안에서 문체가 섞이지 않아야 한다. 6-4b도 `ux-writing-kr`로 진단한 표를 먼저 보여 주고 승인받은 뒤 구현한다.
   - **용어**: 화면의 "발언 ID"는 "발언 번호"로 통일한다(문서·코드 주석의 DB 용어 `utterance_id`는 그대로).
   - 문구가 바뀌면 테스트의 기대 문구와 `data/test/README.md`, 이 문서의 인용 문구도 함께 고친다.
8. **인용 표시의 왼쪽 세로 띠는 의도한 디자인이다** — 2026-11-23 사용자 결정. 원문 인용 카드의 인용문 왼쪽 띠(`components/Quote.tsx`의 `border-l-2 border-accent`)와 원문 보기에서 강조된 발언의 왼쪽 띠(`app/transcripts/[label]/page.tsx`의 `border-l-4`)는 "인용"을 뜻한다. 디자인 훅(impeccable)이 이 둘을 side-tab으로 잡으면 **고치지 않고**, 해당 값만 좁게 무시 설정하고 이유에 "user confirmed: 인용 표시 세로 띠는 의도한 디자인"을 적는다. 2026-11-23 현재 detector가 이 두 파일에서 아무것도 잡지 않아 무시 설정은 아직 없다(`impeccable ignores`로 확인). 잡히면 그 줄에 나온 규칙·값 쌍으로 `ignore-value`를 쓴다. 로딩 뼈대(`components/Skeletons.tsx`)의 발언 줄에서는 훅이 투명 띠를 지적해 같은 폭을 여백(`pl-5`)으로 맞췄다(화면 차이 없음). 무시 설정은 `.impeccable/` 아래 설정 파일에 저장되고 `config.local.json`은 `.gitignore`에 있어 저장소에 올라가지 않으므로, 결정은 이 문서에도 남긴다.

9. **클로바노트 가져오기와 화자 확인 (6-7)** — 2026-11-23 승인. 실제 파일에서 사용자가 확인한 형식: 머리말 3줄(제목, 가운뎃점 "・"이 있는 날짜 줄, 작성자 이름) 뒤에 빈 줄 2개, 화자 줄은 `참석자 1 00:00`(분:초. 긴 녹음을 위해 `H:MM:SS`도 알아본다), 28분 녹음이 약 7,900자.
   - **클로바 모드**: `<표기> <시간>`만 있는 줄이 2개 이상이면, 그 첫 줄 앞은 화자로 읽지 않고 전부 머리말로 제외한다("머리말 N줄 제외"). 제목에 콜론이 있어도 화자로 읽히지 않게 하기 위해서다. 작성자 이름 줄도 저장하지 않는다.
   - **화자 확인**: 지금 규칙으로 역할을 정할 수 없는 파일(모르는 표기가 있고 D10·D12로 막히던 파일)은 저장 전에 화자 확인 단계를 거친다. 역할이 적힌 파일과 `진행자 + 이름 1명`처럼 지금 바로 저장되는 파일은 그대로 저장한다. 고르기 전에는 아무것도 서버로 보내지 않고, 미리보기는 브라우저 안에서만 만든다. 저장할 때 `upload(text, roles)`로 보내고 서버가 같은 규칙으로 다시 검사한다.
   - **역할 규칙**: 진행자는 여러 명이어도 된다(공동 진행자, 기록 담당자). 진행자로 고른 화자의 발언은 `moderator`로 저장되어 근거에서 빠지고 원문은 남는다(DB 구조 변경 없음). 참가자는 적어도 한 명이고, 참가자로 고른 화자는 한 참가자로 합쳐 시간순으로 번호를 붙인다. 발언이 3개 이상인 참가자 화자가 둘 이상이면 여러 명 인터뷰로 보고 "지금은 1:1 인터뷰만 올릴 수 있어요"로 막는다. "줄"은 발언(블록) 수로 센다.
   - **기본값**: 역할 표기가 있는 화자는 그 표기로, 모르는 표기는 처음 말한 화자를 진행자로, 나머지를 참가자로 미리 고른다. 화자가 한 명뿐이면 참가자로 미리 골라 진행자 없이 저장할 수 있다. 1~2줄뿐인 화자는 참가자로 미리 고르고 "N줄뿐이라 인식 오류일 수 있어요. 진행자로 고르면 원문은 남고 근거에서만 빠져요."를 붙인다.
   - **FGI 막힘은 우회할 수 있고 막지 않는다**(결정): 두 번째 참가자를 진행자로 고르면 통과한다. 대신 요약 줄에 "진행자로 고른 발언 N개는 근거로 쓰지 않아요"를 붙여 대가가 보이게 한다.
   - **v1에서 뺀 것**: 본문의 `결론:` 같은 줄이 1줄 화자로 잘못 읽힐 때 "발언이 아니에요(앞 발언에 붙이기)" 선택지는 만들지 않는다. 그 줄은 표기가 사라진 채 참가자 발언으로 저장될 수 있다(안내 문구로만 알린다).
   - **글자 수 한계(10,000자)는 유지한다**: 한 파일에 10,000자는 녹음 약 35분 분량이다(실측: 28분 ≈ 7,900자). 넘었을 때 "나누어 올리기"는 안내하지 않는다. 한 인터뷰를 나누어 올리면 같은 참가자가 파일마다 다른 참가자로 잡혀 "몇 명이 말했나"가 부풀려지기 때문이다. 문구는 사실만 알린다: "지금은 한 파일에 10,000자(녹음 약 35분)까지 올릴 수 있어요." 기존 D2(글자 초과)·C7(파일이 너무 큼)의 "나누어 올려 주세요"를 이 문구로 바꾼다(6-7-1에서 함께 고치고, `lib/transcript.ts`·`components/Upload.tsx`·테스트·`data/test/README.md`의 문구를 맞춘다). 알려진 한계: 35분이 넘는 녹음은 올릴 수 없다.
   - **기존 기대가 바뀌는 `data/test` 파일**: `18_화자3명`(진행자, 참가자, 김테스트)과 `19_구분불가`(김테스트, 이테스트)는 "막힘"에서 "화자 확인"으로 바뀐다. 새 파일 `24_클로바노트형식.txt`는 가짜 이름·가짜 내용, 1줄짜리 참석자 3 하나를 넣는다.

## 데이터 구조 초안 (최종은 `docs/db.md`)

```
transcripts  id, owner_id, participant_label, meta, char_count, created_at
             unique(owner_id, participant_label)
utterances   id, owner_id, transcript_id→transcripts, utterance_id('A-04'), seq,
             speaker_role('participant'|'moderator'), text, embedding(5단계)
             unique(owner_id, utterance_id), unique(id, speaker_role)
insights     id, owner_id, title, summary, created_at
evidence     id, owner_id, insight_id→insights, returned_id(AI가 준 문자열),
             utterance_pk(null 가능), speaker_role 고정 'participant',
             status('verified'|'not_found'|'moderator')
             FK (utterance_pk, speaker_role) → utterances(id, speaker_role)
```

- 근거 테이블에 인용 문장을 저장하지 않는다. 화면은 항상 `utterances`를 조인해 원문을 가져온다.
- 복합 FK로 진행자 발언은 DB 수준에서 근거로 연결할 수 없다.
- 탈락한 ID도 `status`와 함께 남겨 4일차 실패 원인 분석에 쓴다.
- RLS: 네 테이블 모두 `owner_id uuid default auth.uid()`, 정책은 `authenticated`에 `owner_id = auth.uid()` 하나. `anon`은 정책이 없어 0행. `match_utterances`는 호출자 권한으로 실행한다.

## 발언 구분과 저장

전사본은 두 가지 형식으로 읽는다. **AI는 쓰지 않고 규칙만 쓴다**(`lib/transcript.ts`). 브라우저(올리기 전)와 서버(저장 전)에서 같은 함수를 쓰고, 어긋나면 추측하지 않고 줄 번호와 고치는 방법을 알려 주며 중단한다.

- **번호 형식**(지금까지의 형식): 1행 가상 데이터 표시(`[가상 …]`, 형식의 일부라 알리지 않고 넘어간다), 2행 `참가자 X | …` 헤더, 이후 `X-NN 진행자: …` 또는 `X-NN 참가자 X: …`. 정규식 `^([A-Z])-(\d+) (진행자|참가자 ([A-Z])): (.+)$`. `A-02` 같은 줄이 하나라도 있으면 이 형식으로 읽고, 번호가 틀리면 오류다(번호 건너뜀, 라벨 불일치, 콜론 없는 번호 줄). 이전 파서와 같은 결과임을 샘플 8건 등 20개 파일로 비교해 확인했다.
- **번호 없는 형식**(2026-11-23 추가): 발언 번호를 직접 적지 않아도 된다. 화자 표기를 알아보고 번호를 순서대로 붙인다.
- 문장은 앞뒤 공백만 정리해 그대로 저장한다. **원문 글자는 바꾸지 않는다.** 자동 정리는 아래 다섯 가지뿐이다.
- 개인정보 검사는 형식과 상관없이 원본 줄에 그대로 한다(줄 번호도 원본 기준).

### 자동 정리 (결정 기록 6번)

| 정리 | 규칙 |
| --- | --- |
| 번호 붙임 | 번호 없는 형식이면 `라벨-01`부터 순서대로 붙인다. 라벨은 머리말(`참가자 A | …`)에 있으면 그것을, 없으면 저장할 때 **서버가 비어 있는 다음 글자**(A부터, 중간이 비면 그 글자)를 붙인다 |
| 화자 표기 정리 | 아래 표기 목록으로 진행자·참가자를 알아본다. 이름 같은 표기는 역할로만 저장하고 표기는 남기지 않는다 |
| 시간 표시 지움 | 줄 전체가 시간이거나, 줄 맨 앞(`[00:01:23]`, `00:01:23`)이거나, 화자 표기 바로 뒤일 때만 지운다. `01:23 진행자: …`처럼 뒤에 화자 표기가 올 때는 분:초 형태도 지운다. 발언 안의 "3:30에", "12:03"은 그대로 둔다 |
| 여러 줄 합침 | 화자 표기가 없는 줄은 앞 발언에 공백 한 칸으로 이어 붙인다(번호 형식 파일 포함). 번호처럼 보이는데 모양이 틀린 줄은 합치지 않고 오류로 둔다 |
| 머리말 제외 | 첫 발언 앞의 줄은 저장하지 않고 "머리말 N줄 제외"로 알린다(번호 형식의 `[가상 …]` 첫 줄 제외). 머리말에 `녹음 파일: …`처럼 콜론이 있으면 화자 표기로 읽혀 막힐 수 있다(읽은 표기를 알려 준다) |

빈 줄은 말없이 지운다. 결과 카드에는 정리한 것만 한 줄로 알린다. 예: `자동 정리됨: 번호 붙임, 화자 표기 정리, 시간 표시 12개 지움, 여러 줄 3곳 합침, 머리말 2줄 제외`. 정리한 것이 없으면(번호 있는 정상 파일) 이 줄이 나오지 않는다.

### 알아보는 화자 표기 (대소문자 구분 안 함)

| 역할 | 표기 |
| --- | --- |
| 진행자 | 진행자, 인터뷰어, 모더레이터, 사회자, 질문자, `Q`, Interviewer, Moderator, Host |
| 참가자 | 참가자, 응답자, 답변자, 인터뷰이, 사용자, 유저, `A`, Participant, Respondent, Interviewee, User. 뒤에 번호나 글자가 붙은 것(`참가자 1`, `참가자 A`)도 포함 |
| 나머지 | 위에 없는 표기(예: 이름). 진행자 표기가 있고 다른 화자가 한 사람뿐일 때만 참가자로 본다 |

- **줄 모양**: `진행자: 글`, `진행자 : 글`, 전각 `：`, `[진행자] 글`, `진행자> 글`, `Q. 글`, `Q) 글`(마침표·괄호는 `Q`/`A` 한 글자일 때만), 시간이 앞에 붙은 줄, `참가자 1  00:01:23`(글은 다음 줄). 표기는 20자 이하·두 단어 이하이고 콜론 뒤에 숫자가 바로 오는 `3:30`은 화자로 읽지 않는다.
- **저장하지 않고 이유를 알리는 경우**: 화자 표기가 3개 이상(읽은 표기와 줄 수를 알린다), 진행자와 참가자를 구분할 수 없음(진행자 표기가 없고 화자가 둘 이상, 또는 화자가 한 명인데 참가자 표기가 아님), 참가자로 읽을 화자가 없음(진행자 표기만 있음), 화자 표기를 찾지 못함, 번호 있는 줄과 없는 줄이 섞임, 화자 표기만 있고 내용이 없는 발언.
- **저장하는 경우**: 진행자 없이 참가자 표기만 있어도(`참가자:` 줄만) 저장한다.

## 근거 규칙

1. AI 출력 스키마에 인용 문장 자리가 없다. `utterance_ids: string[]`만 받는다.
2. 대조 함수는 `lib/evidence.ts` 하나이고 주제 분류와 검색 · 찾기가 모두 거친다. 정확히 일치하는 ID만 조회한다: 없으면 `not_found`, 진행자면 `moderator`, 참가자면 `verified`. 비슷한 ID를 고쳐 주지 않는다.
3. 화면의 인용은 `verified` 행의 `utterances.text`만 렌더링한다.
4. 검증된 근거가 0개인 인사이트는 "근거 없음" 상태로 표시한다. 검색 · 찾기에서 검증된 문장이 0개면 "원문에서 근거를 찾지 못했어요"로 답한다.

## 의도적 오류 데이터 (사용성 테스트용)

사용성 테스트에서 "잘못된 근거를 찾아내는지" 보는 재료다. 고치지 않는다. 검색 · 찾기의 `MOCK_AI` 가짜 응답(`lib/ai/fixture.ts`의 `mockAnswer`)에 들어 있고, **샘플 8건이 올라와 있을 때** 아래 세 문장을 그대로 돌려준다. 샘플이 아니면 사용자의 전사본에서 번호를 골라 같은 구성(정상 3 / 정상·진행자·없는 번호 / 근거 없음)으로 만든다. 이전에 `lib/mock.ts`에 있던 도서관 앱 오류 데이터는 이 파일과 함께 지웠다(결정 8, 5단계 완료).

| 문장 | 근거 | 코드의 판정 | 화면에서 보이는 모습 |
| --- | --- | --- | --- |
| 1. "반납이 제대로 됐는지 확신하기 어렵다는 말이 여러 번 나왔습니다." | A-08, H-08, C-08 | 셋 다 `verified` | 정상 인용 카드 3개로 보인다. **C-08은 실제 참가자 발언이지만 뜻이 반대다**("반납은 쉬워요. 꽂으면 끝이라. 불만 없어요"). 코드는 못 잡는다. 사람이 읽어야 알 수 있는 오류다 |
| 2. "반납이 처리되지 않아 추가 요금이 나온 경우도 있었습니다." | C-10, A-07, Z-99 | `verified`, `moderator`, `not_found` | C-10만 인용 카드로 보이고, A-07(진행자 발언)과 Z-99(없는 번호)는 "근거 없음"으로 걸러진다 |
| 3. "대부분의 참가자가 앱 사용을 그만두었습니다." | 없음 | 근거 없는 문장 | 기본으로 숨겨지고 "근거 없는 문장 1개 보기"를 펼치면 "근거 없음" 라벨과 함께 보인다 |

재현: `.env.local`에 `MOCK_AI=1`을 넣고 서버를 다시 시작한 뒤 샘플 8건을 올려 둔 상태에서 아무 질문이나 찾는다. 끝나면 `MOCK_AI`를 지운다. 가짜 검색도 하루 30회에 센다.
